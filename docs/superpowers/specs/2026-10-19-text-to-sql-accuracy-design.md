# Text-to-SQL 정확도 개선 1단계 설계 (평가 체계 + 생성 파이프라인 재설계)

## 배경 및 목적

수강신청 도메인 text-to-sql 서비스의 정확도를 끌어올린다. 현재 골든 평가셋(43개) 실행 정확도는 **27.9%**(2026-09 리포트, `backend/eval/reports/`)이며 카테고리별로 `course_filter` 40%, `enrollment_aggregate` 20%, `ambiguous_reject` 20%, `personalized_lookup`·`exclude_completed_courses` 0%다.

근거 자료: 최신 논문·블로그 조사 보고서 `docs/superpowers/research/2026-10-19-text-to-sql-literature-review.md`. 본문의 `[n]`은 그 보고서의 참고문헌 번호다.

## 제약

- 외부 LLM API 사용 금지. 공개 가중치 모델만 로컬에서 실행.
- 서비스 GPU: 12~16GB(로컬, Ollama, Q4_K_M).
- 응답 시간: 질의당 5~10초 허용(캐시 정확 일치는 즉시).
- 학습 서버(2단계용): Tesla P100 16GB × 8, Ubuntu 20.04, CUDA 12.2, 공유 서버(장시간 독점 불가). bf16·FlashAttention 2·vLLM 미지원.
- 작업 브랜치: `feature/t2s-accuracy`(기반 `feature/improve-tts-accuracy` — NER v3, 골든 평가셋 포함).

## 전체 로드맵

| 단계 | 내용 | 산출물 |
|---|---|---|
| **1 (이 문서)** | 평가 체계 확장 + 생성 파이프라인 재설계 + 모델 선정 | 평가셋 ~250개, v2 파이프라인, 선정 모델 |
| 2 (별도 spec) | P100 서버 사전 점검 → 실행 필터링 도메인 합성 데이터 → 선정 모델 QLoRA 학습 → GGUF 변환·투입 | 도메인 LoRA 모델 |
| 범위 밖 | 강화학습(GRPO: P100에서 vLLM 불가·공유 서버), NER 자체 개선, 졸업요건 기능 | |

## 현재 상태에서 확인된 문제

1. **학습-서빙 프롬프트 불일치**: 현재 SQL 모델은 `models/Modelfile`의 고정 SYSTEM(`Table: courses`, 컬럼 10개, alpaca 템플릿)으로 학습됐는데, 서비스는 `backend/prompt.py`로 `v_course_info` 20개 컬럼 + 영어 규칙 30줄을 보낸다.
2. 개인화·이수 과목 제외 질의에서 모델이 `student`/`enrollment`를 참조하지 않는다(프롬프트에 해당 스키마가 사실상 없음).
3. `v_course_info`는 한 과목·분반이 스케줄 수만큼 여러 행이라 `COUNT(*)` 집계가 틀린다.
4. NER 교정 결과로 질문 문장을 덮어써(`corrected_query`) NER 오류가 그대로 전파된다. 캐시도 NER 마스킹 기준이다.
5. Redis 벡터 캐시가 성공한 질의를 자동 저장해 오답이 재사용될 수 있다.
6. 오류 시 1회 "고쳐줘" 재시도는 7B 모델에서 문법 오류 외에는 효과가 작다 [25][27].

## 1. 평가 체계

### 1.1 평가셋 확장 (43 → 약 250)
- 기존 7개 카테고리 유지, 카테고리당 30~40개. 대표 질의를 손으로 작성하고 한국어 변형(약어, 구어체, 조사 생략, 띄어쓰기 오류)을 추가한다.
- 정답 SQL은 사람이 작성하고 실제 DB에서 실행해 결과가 0행이 아니며 과도하지 않음을 확인한 것만 채택한다. 정답 결과가 0행인 케이스는 `empty_gold: true`로 표시하고 정확도 집계에서 별도 보고한다(우연 일치 방지 [46]).
- 평가셋은 고정하며 학습·예시 저장소에 쓰지 않는다(저장소 등록 시 평가셋과 KURE 유사도 0.9 이상이면 거부, 2단계 합성 데이터도 동일 검사).

### 1.2 지표
- **실행 정확도(EX)**: 기존 `grading.py` 방식(결과 행 순서 무관 집합 비교) 유지. 단 `backend/eval/README.md`의 알려진 채점 왜곡 두 가지를 고친다.
  - 스케줄 확장: 파이프라인이 요일·시간 필터 결과를 해당 과목의 전체 스케줄 행으로 확장하므로, 채점 시 정답 SQL에도 같은 `expand_schedule_filtered_course_rows`를 적용한다(기존 6개 케이스가 이 이유로 어긋남).
  - 단일 컬럼 관대함: 정답 결과에 `subject_code`·`section`이 있으면 생성 결과에도 두 컬럼이 있어야 하고 비교 컬럼에 포함한다(컬럼 1개만 투영해 우연히 통과하는 것 방지).
- **Soft-F1** [48]: 컬럼 순서·일부 누락 허용 보조 지표.
- 테스트 스위트 정확도 [47](DB 변형본 재채점)는 1단계 범위 밖.

### 1.3 단계 분리 평가 [36]
- **실제 흐름(vanilla)**: 파이프라인 그대로.
- **분리(decoupled)**: 평가셋에 기록한 정답 값 힌트를 강제로 넣고 생성만 채점 → 값 매칭과 생성 중 어디서 틀리는지 분리.
- 리포트: 카테고리별 EX, 실패 유형(실행 오류 / 결과 불일치 / 빈 결과 / 거부 오판), p50·p95 응답 시간, 사용 설정.

### 1.4 판단 기준
- 250개 기준 1문제 = 0.4%p. 개선안은 **+3%p 이상**일 때만 채택.
- 1단계 목표: 실행 정확도 **60% 이상**(현재 기본적 실패가 많은 상태를 근거로 한 판단 목표이며 문헌 수치가 아님), p95 응답 시간 10초 이하.

## 2. 모델 선정과 서빙

### 2.1 후보 (모두 Q4_K_M, 로컬 Ollama)

| 후보 | 크기 | 근거 |
|---|---|---|
| 현재 파인튜닝 모델 | 7B | 기준선 |
| Qwen2.5-Coder-7B-Instruct | 7B | 현재 모델의 베이스 |
| XiYanSQL-QwenCoder-7B-2504 | 7B | PostgreSQL 지원, M-Schema 학습 [9] |
| OmniSQL-7B | 7B | BIRD-dev 63.9 / 다수결 66.1 [14] (SQLite 중심 학습) |
| XiYanSQL-QwenCoder-14B-2504 | 14B(~9GB) | BIRD-dev 65.3 [9] |

- 공식 GGUF가 없으면 llama.cpp 변환 스크립트로 직접 만든다.
- Arctic-Text2SQL-R1 [10]은 긴 추론 출력으로 응답 시간 제약에 맞지 않아 1단계 제외.

### 2.2 선정 규칙
v2 파이프라인(3장)에 후보를 하나씩 끼워 확장 평가셋으로 측정한다. **EX 최고이면서 p95 ≤ 10초**인 모델을 선정하고, EX 차이가 3%p 이내면 더 작은·빠른 모델을 고른다. 선정 모델은 2단계 LoRA의 베이스가 된다.

### 2.3 서빙
- SQL 생성 모델 1개만 상주. 후보 N개는 Ollama 병렬 요청(`OLLAMA_NUM_PARALLEL`)으로 동시 생성.
- `backend/llm.py`의 alpaca 템플릿 호출은 모델 기본 채팅 템플릿(`/api/chat`) 호출로 교체한다.

## 3. v2 생성 파이프라인

```
질문 (+ 로그인 학생)
 ① 값 후보      NER v3 + n-gram rapidfuzz DB 값 검색 → 컬럼별 후보 최대 3개(점수순)
 ② 예시 검색    검증된 예시 저장소에서 (마스킹 질문, 원문 질문) 두 기준 KURE 유사도로 검색·병합,
                SQL 골격이 겹치지 않게 다양화해 k=4 [35]
                └ 정확 일치(마스킹 질문 유사도 ≥ 0.95 & 마스크 구성 동일 & NER 결과 존재)
                  → 저장된 SQL에 값 채워 즉시 실행·응답
 ③ 프롬프트     M-Schema [9] + 한국어 도메인 규칙 + 값 후보 + 예시 4개 + 학생 자리표시자
 ④ 후보 생성    N=5 (온도 0 1개 + 샘플링 4개, 샘플마다 예시 순서 셔플 [3])
 ⑤ 후보별 처리  SQL 추출 → validate.py → 기존 실행 전 변환(스케줄 확장, 이수 과목 제외)
                → 실행(statement_timeout 3초, 학번 파라미터 바인딩)
 ⑥ 다수결      결과 집합 서명으로 묶어 최대 묶음 선택 [14][15]
                오류 후보 제외, 빈 결과는 후순위, 동점 시 온도 0 후보 우선
                후보 과반이 UNKNOWN이면 확인 질문 응답
 ⑦ 재시도      모든 후보가 오류 또는 빈 결과일 때만 1회, 오류 메시지/“결과 없음”을 피드백 [25]
 ⑧ 응답        기존 응답 형식 유지 + 후보·소요 시간 로그
```

### 3.1 값 후보 (NER 의존도 축소)
- 원문 질문은 **수정하지 않고** 그대로 모델에 준다. NER 결과는 "참고용, 틀릴 수 있음" 힌트로만 쓴다.
- NER과 독립적인 두 번째 경로: 질문의 2~4음절 n-gram을 학과명·과목명·교수명·이수구분 DB 값 목록과 rapidfuzz로 대조(CHESS [6]의 값 검색을 경량화).
- 두 경로 결과를 병합해 컬럼별 최대 3개. 분리 평가에서 NER만 / n-gram만 / 둘 다를 비교해 NER 존치를 데이터로 결정한다.

### 3.2 카테고리별 대응
- **개인화·이수 과목 제외**: 프롬프트에 "현재 로그인 학생 = `%(student_id)s`"와 `student`·`enrollment` 스키마를 항상 포함. 모델은 자리표시자를 그대로 쓰고 실행 시 파라미터 바인딩한다(`validate.py` 자리표시자 규칙과 일치, 학번이 SQL 문자열에 들어가지 않음).
- **집계**: "과목 수는 `COUNT(DISTINCT (subject_code, section))`" 규칙 + 예시.
- **모호 질의**: `UNKNOWN` 출력 허용, 후보 과반 `UNKNOWN`이면 확인 질문 응답.

### 3.3 검증된 예시 저장소 (기존 벡터 캐시 대체)
- 자동 저장을 중단한다. 초기 시드는 사람이 검토한 약 150개(질의 유형별 대표 SQL 골격: 학과+요일+이수구분, 선수과목, 집계, 개인화, 이수 과목 제외, 시간 범위 등).
- 평가셋과 유사도 0.9 이상 예시는 등록 거부.
- 운영 질의는 "검토 대기" 로그에만 쌓고 승인 스크립트로 등록한다(Snowflake Verified Query Repository 방식 [12]).
- 저장 매체는 기존 Redis + KURE 인덱스를 재사용한다.

## 4. 프롬프트

- 구조: system 지시(PostgreSQL SELECT 1개만 출력, 모호하면 `UNKNOWN`) → M-Schema → 한국어 도메인 규칙(10줄 이내) → 값 후보 → 예시 4쌍 → user 질문.
- **M-Schema 자동 생성**: 스크립트가 DB에서 타입과 값을 읽어 생성. 고유값 ≤ 20인 컬럼은 전체 값, 그 외는 예시 3개. 테이블 설명(“한 과목·분반이 요일·시간 수만큼 여러 행”)과 FK 관계 표기. 한국어 컬럼 설명은 사람이 관리하는 YAML 하나.
- **도메인 규칙**: 기존 영어 규칙 30줄 중 효과 있는 것만 한국어로 압축(과목 수 집계, 1시~7시 → 13~19시, 오전/오후, 학과·과목명 LIKE, 값 후보가 있는 이수구분은 =, 학생 자리표시자). 규칙별 효과는 평가로 검증한다.
- 출력은 SQL만(추론 출력 없음, 응답 시간 제약).
- 예상 길이 1,500~2,500 토큰.

## 5. 코드 구조, 예외 처리, 테스트

### 5.1 모듈 (`backend/t2s/` 신규)

| 모듈 | 책임 |
|---|---|
| `values.py` | NER 결과 + n-gram rapidfuzz → 컬럼별 값 후보 |
| `examples.py` | 검증된 예시 저장소: 검색, 정확 일치 판정, 등록·승인 |
| `schema_doc.py` | DB + 한국어 설명 YAML → M-Schema 텍스트(캐시) |
| `prompt.py` | 채팅 메시지 조립 |
| `generate.py` | Ollama `/api/chat` 호출, N개 병렬 생성, SQL 추출 |
| `execute.py` | 후보별 검증 → 기존 실행 전 변환 → 실행(타임아웃, 학번 바인딩) |
| `vote.py` | 결과 집합 서명·다수결(순수 함수) |
| `pipeline.py` | ①~⑧ 조립, 재시도, 응답·로그 |

- 설정(N, 온도, k, 예시 사용, 값 검색 경로, 모델명)은 환경변수로 노출해 평가 스크립트가 ablation을 돌릴 수 있게 한다.
- 기존 `prompt.py`·`rag.py`·`llm.py`·`process.py`·`vector_cache.py`는 v1 경로로 유지하고, `keyword_extract.py`·`validate.py`·실행 전 변환 함수는 v2에서 재사용한다.

### 5.2 예외 처리
- Ollama 장애/타임아웃: 이미 생성된 후보로만 다수결, 후보 0개면 기존과 같은 오류 응답.
- SQL 실행 타임아웃: 해당 후보만 탈락(`statement_timeout` 3초).
- 재시도 후에도 전부 실패: 오류 응답 + 실패 로그(2단계 오류→수정 학습 데이터로 활용).
- 모든 후보에 `validate.py` 검증 적용(SELECT 전용, 테이블 허용 목록, 학생 범위). 학번은 파라미터 바인딩만 허용.

### 5.3 테스트
- 단위(TDD, DB/LLM 없음): `vote`, `values`, `schema_doc`, `prompt`, `examples` 판정 로직.
- 통합: 가짜 LLM으로 파이프라인 전체(일부 후보 실패, 전부 UNKNOWN, 정확 일치, Ollama 부분 장애).
- 평가 실행: 실제 DB·Ollama로 모델 비교와 ablation(예시 유무, N=1 vs 5, 값 검색 경로 3종).

### 5.4 전환
- `T2S_PIPELINE=v2` 환경변수로 전환. 평가에서 v1 대비 +3%p 이상이고 p95 ≤ 10초면 기본값을 v2로 바꾼다.
- 현재 파인튜닝 모델과 v1 경로는 기준선으로 유지하고 2단계 후 정리한다.
